۱. رویکرد طراحی

داخل هر ماژول، Application به شکل feature/use-case محور سازمان‌دهی می‌شود. به‌جای پوشه‌های سراسری Commands/Queries/Handlers، فایل‌های یک قابلیت مانند ActivateAutomation کنار هم قرار می‌گیرند. هدف کاهش پراکندگی و بالا بردن فهم موضعی است.

Automations/ Domain/Automations/... Application/ActivateAutomation/{Command,Handler,Validator} Infrastructure/{Persistence,MetaAdapters}

۲. طراحی Domain

Domain فقط وقتی پیچیدگی کسب‌وکار وجود دارد رفتار، invariant، value object و event می‌گیرد. DDD تشریفاتی ممنوع است؛ هر read model ساده به Aggregate/Factory احتیاج ندارد. قواعد مهم Automation، authorization-sensitive semantics و state transitionها باید deterministic و قابل unit test باشند.

۳. طراحی Application

هر use case ورودی، context مجوز، orchestration، port و خروجی مشخص دارد و بدون ASP.NET قابل تست است. Interface زمانی ساخته می‌شود که boundary واقعی وجود دارد. تراکنش DB نباید توهم atomic بودن API خارجی ایجاد کند؛ retry/idempotency صریح طراحی می‌شوند.

۴. طراحی API

Endpoint یا Minimal API تنها mapping HTTP و فراخوانی Application را انجام می‌دهد. business logic در endpoint ممنوع است. Problem Details، pagination، correlation، versioning و authorization باید convention واحد داشته باشند تا API با رشد ماژول‌ها ناهمگون نشود.

۵. طراحی Integration خارجی

DTO خام Meta در Infrastructure می‌ماند و به contract داخلی تبدیل می‌شود. timeout، resilience و redaction برای HttpClientها متناسب با operation تنظیم می‌شود. Fixtureهای تست باید synthetic/scrubbed باشند و CI به Meta واقعی متکی نباشد.

۶. طراحی Frontend و Penpot

Frontend تنها Next.js/TypeScript است و feature-based می‌ماند. Penpot visual source of truth است و هر Screen قبل از پیاده‌سازی باید frame، responsive target، token، component variant، state matrix و accessibility note داشته باشد. خروجی HTML/CSS تولیدشده توسط ابزار طراحی مستقیماً architecture production محسوب نمی‌شود.

۷. طراحی Persistence

Persistence در Infrastructure همان ماژول قرار دارد. Generic Repository که قابلیت‌های EF را بی‌دلیل پنهان کند پیش‌فرض نیست. Port/Repository هنگامی ایجاد می‌شود که use case یا aggregate به contract پایدار نیاز دارد. Queryهای سنگین می‌توانند read service اختصاصی داشته باشند.

۸. Background Processing

اسکلت عمداً queue library انتخاب نکرده است. M04/M06 بر اساس durable ingestion، retry، scheduling و observability انتخاب می‌کند. Domain به vendor queue وابسته نمی‌شود و Jobها باید identity/idempotency پایدار داشته باشند.

۹. خطا، resilience و observability

خطاها به validation، authorization، not-found/conflict، provider permanent/policy، transient و internal دسته‌بندی می‌شوند. فقط عملیات safe retry می‌شوند. log ساختاریافته correlation و شناسه‌های امن دارد و token/raw sensitive payload را ثبت نمی‌کند.

۱۰. چک‌لیست Design Review

  • مالکیت module روشن است.
  • dependency رو به داخل است.
  • Workspace/security boundary مشخص است.
  • duplicate/retry/concurrency semantics روشن است.
  • سطح تست درست انتخاب شده است.
  • UI stateهای Penpot کامل‌اند.
  • data ownership/migration impact بررسی شده است.
  • trade-off معماری در ADR ثبت شده است.
