۱. راهبرد دیتابیس

قاصدک با یک PostgreSQL 18 آغاز می‌شود تا عملیات ساده بماند، اما هر business module schema منطقی خودش را دارد. این تصمیم بین سادگی deployment و مرزهای DDD تعادل ایجاد می‌کند و امکان extraction آینده را از بین نمی‌برد.

۳. قواعد مالکیت

  • فقط Infrastructure ماژول مالک migration/table خود است.
  • ماژول دیگر table را مستقیم query/update نمی‌کند.
  • cross-schema FK/view پیش‌فرض ممنوع و نیازمند ADR است.
  • ارتباط بین ماژول‌ها با ID پایدار و contract/event انجام می‌شود.

۴. شناسه و زمان

UUIDv7 گزینه پیش‌فرض شناسه داخلی server-generated است مگر Domain شناسه قوی‌تری نیاز داشته باشد. Instantهای زمانی با timestamptz ذخیره و UTC معنا می‌شوند؛ timezone کسب‌وکار یا کاربر مفهوم جداگانه است.

۵. مدل منطقی اولیه

Identity: Workspace/User/Membership؛ Instagram: Connection/CredentialMetadata/WebhookInbox؛ Conversations: Conversation/Message؛ Automations: Automation/Version/Execution/EffectAttempt؛ Contacts: Contact/SocialIdentity/Tag/Note؛ Billing: Plan/Subscription/Entitlement/ProviderEvent. نام جدول‌ها تا milestone پیاده‌سازی frozen نیستند.

۶. Idempotency و Event Processing

Webhook ماهیت at-least-once دارد. unique provider delivery/event key یا کلید dedup تأییدشده باید در DB enforce شود. علاوه بر inbox، effect identity برای action لازم است چون internal retry می‌تواند پس از بخشی از پردازش رخ دهد. M04/M06 طراحی نهایی Inbox/Outbox/Effect Ledger را مشخص می‌کند.

۷. امنیت و Index

credential DB runtime-injected است. token متا پیش از تکمیل M03 باید at-rest محافظت شود و backup نیز داده حساس محسوب می‌شود. Index از query واقعی ساخته می‌شود؛ workspace owner key، external IDs، webhook IDs، conversation recency و execution status کاندیدهای اولیه‌اند.

۸. Migration

Migrationها module-owned هستند و در فرایند کنترل‌شده deploy اجرا می‌شوند. instanceهای متعدد نباید آزادانه migration destructive را race کنند. تغییر ناسازگار باید expand/migrate/contract یا sequence مناسب داشته باشد. هر migration با PostgreSQL واقعی container test می‌شود.

۹. تست، Backup و Recovery

برای semantics دیتابیس از Testcontainers PostgreSQL استفاده می‌شود نه in-memory fake. قبل از production، backup خودکار، retention، integrity check، restore در محیط پاک و smoke test اپلیکیشن عملاً تمرین می‌شود؛ RPO/RTO بعد از نیاز واقعی کسب‌وکار تعیین می‌شود.
