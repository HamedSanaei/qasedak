M13-001

بازبینی قرارداد فعلی Meta و اینستاگرام

پیش‌نیاز قطعی
هدف: قبل از هر تغییر Production، تمام فرض‌های Qasedak درباره Instagram Login، توکن‌ها، Messaging، Private Reply، Webhook، Conversations API، Media، Insights، App Review و محدودیت‌های سیاستی با مستندات رسمی و فعلی Meta دوباره تثبیت می‌شوند.

چه چیزی به Qasedak اضافه می‌شود؟

  • ماتریس رسمی قابلیت‌ها و محدودیت‌ها بر اساس نسخه فعلی Meta.
  • تفکیک قابلیت‌های پشتیبانی‌شده، خارج از Scope، نیازمند App Review/Advanced Access و قابلیت‌های غیرقابل اتکا.
  • تعیین دقیق Graph host/version، permissionها، token typeها، messaging windowها و webhook fieldهای معتبر.
  • اصلاح مستندات قدیمی پروژه در صورت تغییر قرارداد Meta.

مثال کاربردی

اگر مستندات قدیمی پروژه بگویند ارسال پیام فقط از مسیر Facebook Login ممکن است ولی قرارداد فعلی Meta مسیر Instagram Login را پشتیبانی کند، این تسک مرجع نهایی را اصلاح می‌کند و تسک‌های بعدی فقط بر اساس نتیجه جدید جلو می‌روند.

چک‌لیست تست در Production / Staging

نشانه خرابی: اگر بعد از این تسک هنوز چند سند داخلی درباره یک قابلیت حرف متناقض بزنند، M13-001 کامل نشده است.
M13-002

اتصال تمام گفتگوها و Automationها به اکانت دقیق اینستاگرام

اصلاح معماری حیاتی
هدف: هر رویداد، Conversation، Reply و Automation باید به ConnectedAccount دقیق خودش متصل باشد؛ نه فقط Workspace و نه «اولین اکانت فعال».

چه چیزی به Qasedak اضافه می‌شود؟

  • افزودن ChannelAccountId / ConnectedAccountId به هویت کانال.
  • تفکیک Conversationهای یک Participant یکسان در دو اکانت Instagram.
  • ارسال Reply فقط با Token همان اکانتی که Conversation متعلق به آن است.
  • اجرای Automation فقط برای اکانت مربوط به همان Event.

مثال کاربردی

در یک Workspace دو اکانت @shop_a و @shop_b متصل‌اند. کاربر 12345 به هر دو DM می‌دهد. باید دو Conversation مستقل ایجاد شود. Reply از Conversation مربوط به @shop_a هرگز نباید با توکن @shop_b ارسال شود.

چک‌لیست تست در Production / Staging

نشانه خرابی: ادغام دو Thread، ارسال پیام از اکانت اشتباه، یا اجرای Automation بین دو Account یک شکست Critical است.
M13-003

Graph Transport نسخه‌دار و خطاهای استاندارد

زیرساخت Meta
هدف: تمام ارتباط با Graph API از یک زیرساخت استاندارد، versioned، قابل تست و secret-safe عبور کند؛ ولی clientهای تخصصی Media/Messaging/Insights جدا باقی بمانند.

چه چیزی به Qasedak اضافه می‌شود؟

  • Graph API version و host مرکزی.
  • URI builder مشترک و HttpClientهای typed/named.
  • Parser واحد برای code/subcode/fbtrace_id.
  • طبقه‌بندی TokenExpired، Permission، RateLimit، MessagingWindow، Timeout و خطاهای transient.
  • حذف Token و Secret از log و URLهای گزارش‌شده.

مثال کاربردی

اگر Meta برای یک درخواست کد 190 برگرداند، سیستم باید آن را به خطای Token Invalid/Expired نگاشت کند و fbtrace_id را برای عیب‌یابی نگه دارد؛ بدون اینکه access token در log ظاهر شود.

چک‌لیست تست در Production / Staging

نشانه خرابی: ساخت URLهای Meta به‌صورت پراکنده، error handling متفاوت در clientها، یا نشت Token یعنی این لایه ناقص است.
M13-004

صف کارهای زمان‌بندی‌شده و پایدار روی PostgreSQL

Restart-safe
هدف: کارهای زمان‌دار مثل Token Refresh، Follower Snapshot، Reconciliation، Read Fallback و Follow-up بعد از Restart یا Crash از بین نروند.

چه چیزی به Qasedak اضافه می‌شود؟

  • Job پایدار با idempotency key، due time، attempt و status.
  • Lease/claim اتمیک برای چند worker.
  • Retry با backoff و terminal/dead-letter state.
  • بازیابی job بعد از Crash یا پایان lease.
  • Payload بدون access token یا Meta DTO.

مثال کاربردی

یک Follow-up برای ۱۰ دقیقه بعد ثبت می‌شود. سرویس را دقیقه ۵ خاموش و دقیقه ۱۲ روشن می‌کنی. Job باید بعد از Restart یک‌بار اجرا شود؛ نه گم شود و نه دوبار ارسال شود.

چک‌لیست تست در Production / Staging

نشانه خرابی: گم شدن Job بعد Restart، اجرای دوباره، یا ذخیره Secret در جدول jobها Critical است.
M13-005

تکمیل چرخه اتصال اکانت، Profile، Webhook Subscription و Token Refresh

Account lifecycle
هدف: اتصال Instagram از یک OAuth ساده به چرخه کامل Connection تبدیل شود: هویت حرفه‌ای صحیح، Profile، subscription health، OAuth state امن و refresh خودکار Token.

چه چیزی به Qasedak اضافه می‌شود؟

  • OAuth state کوتاه‌عمر، workspace-bound، integrity-protected و replay-resistant.
  • تشخیص professional account identity صحیح برای Messaging/Webhook.
  • ذخیره username، display name، avatar و metadata امن.
  • Subscription/Resubscribe و health وضعیت webhook.
  • Refresh خودکار Token نزدیک انقضا با lock/account claim.

مثال کاربردی

کاربر اتصال Instagram را از Workspace A شروع می‌کند. اگر callback را با state دستکاری‌شده یا در Workspace B مصرف کند، اتصال باید رد شود. اتصال معتبر باید Profile و وضعیت subscription را بدون نمایش Token در UI نشان دهد.

چک‌لیست تست در Production / Staging

نشانه خرابی: OAuth state قابل replay، refresh همزمان ناسازگار، یا اتصال به ID اشتباه از مشکلات امنیتی جدی است.
M13-006

کاتالوگ Media و انتخاب Post/Reel واقعی

Media
هدف: Qasedak بتواند Post/Reel/Video/Carouselهای اکانت متصل را به‌صورت محدود و صفحه‌بندی‌شده بخواند تا Automation به Media واقعی bind شود.

چه چیزی به Qasedak اضافه می‌شود؟

  • Media client تخصصی با cursor pagination.
  • مدل Qasedak برای caption، media type، permalink، thumbnail، likes/comments و timestamp.
  • Hard cap برای جلوگیری از پیمایش بی‌نهایت.
  • API امن برای Post Picker بر اساس ConnectedAccountId.

مثال کاربردی

در Automation Builder اکانت @shop_a انتخاب می‌شود و سپس فقط پست‌های همان اکانت برای انتخاب Trigger نمایش داده می‌شوند؛ پست‌های @shop_b نباید وارد لیست شوند.

چک‌لیست تست در Production / Staging

نشانه خرابی: مخلوط شدن Media بین اکانت‌ها، loop صفحه‌بندی، یا expose شدن Meta DTO مستقیم به frontend نشانه نقص است.
M13-007

Insights، آمار Media و تاریخچه Follower

Analytics
هدف: آمار قابل پشتیبانی Meta برای Media و رشد Followers در Qasedak ذخیره و نمایش داده شود، با graceful degradation وقتی permission یا metric وجود ندارد.

چه چیزی به Qasedak اضافه می‌شود؟

  • Insights client با metricهای معتبر بر اساس media type.
  • bounded concurrency برای چند درخواست insight.
  • Follower snapshot روزانه برای هر ConnectedAccount.
  • تمایز داده observed از backfilled/derived.
  • Overview API برای media totals، follower count و history.

مثال کاربردی

اگر Insights یک Reel metric خاص را ندهد، Media همچنان در کاتالوگ دیده شود و UI فقط همان metric را unavailable نشان دهد؛ نه اینکه کل صفحه خطا شود.

چک‌لیست تست در Production / Staging

نشانه خرابی: خرابی کامل dashboard به‌خاطر یک metric unavailable یا overwrite شدن snapshot معتبر، طراحی مطلوب نیست.
M13-008

تکمیل Webhook Normalization برای Comment، Message، Postback و Read

Event pipeline
هدف: Webhook خام Meta پس از HMAC و Durable Inbox به Eventهای تمیز Qasedak تبدیل شود؛ بدون ورود DTOهای Meta به ماژول‌های دیگر.

چه چیزی به Qasedak اضافه می‌شود؟

  • Comment event با ConnectedAccount دقیق، mediaId و original_media_id.
  • Postback event مستقل.
  • Read/Seen event مستقل طبق contract فعلی.
  • فیلتر echo، self event، deleted، unsupported و attachment-only طبق policy.
  • حفظ unknown fragment برای observability.

مثال کاربردی

Meta یک comment مربوط به boosted media با original_media_id می‌فرستد. Qasedak باید بتواند آن را به Automation مربوط به پست اصلی وصل کند، بدون اینکه raw Meta JSON وارد Automations شود.

چک‌لیست تست در Production / Staging

نشانه خرابی: اجرای business logic سنگین داخل endpoint webhook، نشت DTO یا trigger شدن Automation با echo از مشکلات جدی است.
M13-009

اصلاح Comment Automation به Private Reply واقعی

Critical correctness
هدف: Comment → DM دیگر از مسیر Direct Message عادی انجام نشود؛ اولین تماس Comment باید از operation مخصوص Private Reply با comment identity انجام شود.

چه چیزی به Qasedak اضافه می‌شود؟

  • سه operation مجزا: Direct Message، Comment Private Reply و Public Comment Reply.
  • Global semantic claim برای ConnectedAccountId + CommentId + PrivateReply.
  • Policy boundary برای window/rules فعلی Meta.
  • ثبت outcome مستقل برای Public Reply و Private Reply.

مثال کاربردی

دو Automation روی کلمه «قیمت» فعال‌اند و یک Comment «قیمت؟» می‌رسد. هر دو ممکن است match شوند، ولی فقط یک Private Reply مجاز است. Claim سراسری باید قبل از تماس با Meta جلوی ارسال دوم را بگیرد.

چک‌لیست تست در Production / Staging

نشانه خرابی: دو Private Reply برای یک Comment یا استفاده از recipient.id برای first-contact comment یک شکست مستقیم این تسک است.
M13-010

پیام‌های تعاملی: Text، Postback Button و Link Button

Interactive messaging
هدف: ارسال Direct/Private Reply فقط متن ساده نباشد و قالب‌های تعاملی پشتیبانی‌شده به قراردادهای داخلی Qasedak تبدیل شوند.

چه چیزی به Qasedak اضافه می‌شود؟

  • Plain text.
  • Postback button.
  • Web URL button.
  • Validation مرکزی برای طول متن، URL، payload و تعداد button.
  • Typed success شامل provider message identity.
  • Fallback کنترل‌شده فقط برای خطاهایی که safe هستند.

مثال کاربردی

Private Reply اولیه می‌گوید «برای دریافت لینک بزن» و یک دکمه Postback دارد. کلیک کاربر Postback event تولید می‌کند و ادامه Flow را فعال می‌کند.

چک‌لیست تست در Production / Staging

نشانه خرابی: Fallbackی که محدودیت یک‌بار Private Reply را دور بزند یا validation را به Meta واگذار کند خطرناک است.
M13-011

Opening Private Reply → Postback → Reveal و Follow Gate مشروط

مشروط به Meta
هدف: Flow تعاملی کامل شود: Comment، Private Reply اولیه، کلیک دکمه، correlation امن و سپس Direct Message reveal. Follow Gate فقط در صورت پشتیبانی رسمی قرارداد فعلی Meta فعال می‌شود.

چه چیزی به Qasedak اضافه می‌شود؟

  • Correlation opaque/signed یا persisted برای Postback.
  • اعتبارسنجی Workspace، ConnectedAccount، Automation Version و intended operation.
  • Direct-message reveal idempotent.
  • Read fallback زمان‌بندی‌شده در صورت پشتیبانی.
  • Relationship/follow lookup سه‌حالته فقط اگر Meta واقعاً اجازه دهد.

مثال کاربردی

کاربر روی پست «کلمه GUIDE را کامنت کن» می‌نویسد GUIDE. سیستم یک Private Reply با دکمه «دریافت راهنما» می‌فرستد. پس از کلیک، Postback اعتبارسنجی و یک Direct Message شامل لینک راهنما ارسال می‌شود.

چک‌لیست تست در Production / Staging

نشانه خرابی: اعتماد به payload قابل جعل، reveal دوباره، یا استفاده از scraping برای Follow Status غیرقابل قبول است.
M13-012

تکمیل Automation: Post Scope، DM Trigger، Public Reply و Follow-up

Automation parity
هدف: قابلیت‌های اصلی Automation تکمیل شوند بدون اینکه evaluator به شبکه، ساعت واقعی، Token یا randomness وابسته شود.

چه چیزی به Qasedak اضافه می‌شود؟

  • Trigger بر اساس Comment یا inbound DM.
  • Specific Post / Any Post / original-media mapping.
  • Keyword / Any Word / Whole Word / Every Comment.
  • Public reply، Direct/Private Reply، reveal و follow-up.
  • ذخیره configuration در Definition Version.
  • انتخاب reply pool یک‌بار و persist برای retry قابل بازتولید.

مثال کاربردی

Automation فقط روی Reel شماره X فعال است؛ اگر متن Comment شامل کلمه کامل «قیمت» بود Public Reply بزند و Private flow را شروع کند، سپس ۳۰ دقیقه بعد در صورت معتبر بودن window یک Follow-up ارسال کند.

چک‌لیست تست در Production / Staging

نشانه خرابی: network call داخل evaluator، randomness تکرارنشدنی یا trigger شدن automation روی media/account اشتباه شکست معماری است.
M13-013

بازیابی Commentهای از دست‌رفته و Sync تاریخچه Conversation

Recovery & sync
هدف: Webhook تنها منبع حقیقت نباشد؛ Comment یا Conversationهایی که به هر دلیل از webhook وارد نشده‌اند به‌صورت محدود، idempotent و account-aware بازیابی شوند.

چه چیزی به Qasedak اضافه می‌شود؟

  • Phase A: Comment reconciliation برای mediaهای فعال.
  • Phase B: Conversations API history import.
  • cursor/hard cap و rate-limit-aware scheduling.
  • dedup بین webhook و reconciliation.
  • import/upsert از طریق قرارداد Conversations؛ بدون نوشتن مستقیم Instagram Infrastructure در schema آن.

مثال کاربردی

در زمان قطعی سرویس یک Comment وارد Meta شده ولی webhook به Qasedak نرسیده. Reconciliation بعدی آن را می‌یابد و همان pipeline عادی را اجرا می‌کند، ولی اگر webhook دیرتر برسد اثر دوم ایجاد نمی‌شود.

چک‌لیست تست در Production / Staging

نشانه خرابی: ساخت pipeline دوم برای Automation یا duplicate شدن history بعد resync نشان می‌دهد ادغام درست انجام نشده است.
M13-014

سطح کامل Frontend برای قابلیت‌های واقعاً پشتیبانی‌شده

Frontend
هدف: تمام capabilityهای تأییدشده M13 از طریق APIهای authenticated و UI موجود Qasedak قابل استفاده باشند، بدون expose کردن Meta DTO، Token یا feature جعلی.

چه چیزی به Qasedak اضافه می‌شود؟

  • Account/Profile/Subscription health.
  • Media picker و Analytics.
  • Sync status و manual resync.
  • Automation Builder با account/post/trigger/opening/reveal/link/public reply/follow-up.
  • stateهای Unsupported، Permission Missing، Disconnected، Unhealthy و Temporary Failure.
  • Penpot-governed UI.

مثال کاربردی

اگر Follow Gate طبق M13-001 پشتیبانی نشود، UI نباید یک سوییچ فعال و فریبنده نشان دهد؛ باید آن را حذف یا با توضیح صحیح غیرفعال کند، در حالی که بقیه Automation Builder کار می‌کند.

چک‌لیست تست در Production / Staging

نشانه خرابی: کنترل فعال برای feature unsupported، API call مستقیم Browser به Meta یا نشت Token در response یک شکست جدی است.
M13-015

Compliance، App Review و گیت نهایی Production

Final gate
هدف: در پایان، کل M13 با تست‌های deterministic، PostgreSQL واقعی، mocked Meta، runbook و ماتریس compliance قابل اثبات باشد.

چه چیزی به Qasedak اضافه می‌شود؟

  • Contract test برای همه Graph adapterها و webhook fixtureها.
  • E2E برای multi-account، Private Reply concurrency، restart، retry و sync.
  • Metrics برای Graph، token refresh، subscriptions، queue، sends، automation و rate limits.
  • Runbook Production و App Review/Advanced Access checklist.
  • ماتریس شش‌حالته وضعیت هر capability.

مثال کاربردی

قبل از release، یک سناریوی کامل comment → opening private reply → postback → reveal → follow-up با Meta mock و PostgreSQL واقعی اجرا می‌شود، سپس smoke محدود Production مطابق runbook انجام می‌گیرد.

چک‌لیست تست در Production / Staging

نشانه خرابی: اگر release به live Meta call در CI وابسته باشد، capabilityهای unsupported مخفی شوند، یا runbook production نداشته باشیم، M13 کامل نیست.

ماتریس تست Production / Staging

این سناریوها را بعد از تکمیل تسک‌های مربوطه به‌عنوان Smoke و Regression دستی نگه دار. برای عملیات مخرب یا Rate Limit بهتر است ابتدا Staging/Meta test accounts استفاده شود.
